## Audit (2026-09-17, branch `0.3.3`)

### Two parallel theme systems, both hardcoded in TypeScript and dark-only
- **Interface themes.** `ATLAS_THEMES` in `src/features/theme/themes.ts:57` defines 6 themes (atlas-black, chyral, mirage, rose-pine, one-dark, phosphor). Each has 17 hex fields, which `buildThemeVars` (:236) turns into 33 CSS vars. `apply-atlas-theme.ts:19` sets them as inline styles on `<html>`.
- **Editor themes.** `EDITOR_THEMES` in `src/features/editor/themes/themes.ts` defines 10 themes (atlas, atlas-mono, dracula, one-dark, monokai, tokyo-night, catppuccin frappé/macchiato/mocha, vesper). Each has 37 colours, which become the 33 `--cm-*` / `--diff-*` vars.
- **Persistence.** `config.toml` stores `atlasTheme` and `codeEditorTheme` (`src-tauri/src/state/atlas_config.rs:137-142`). Ids are not validated, and an unknown id silently falls back to the default.
- **Startup.** Both are applied from `project-store.ts` (hydrate at :486, settings side effects at :308).

### Token sprawl
- **Two definition sites.** `src/styles/tokens.css` defines 170 vars on `:root`. `globals.css:10-129` holds 64 `@theme inline` entries.
- **Duplicate names for one colour.** For example, `--bg-surface` = `--bg-primary` = `--background`. There are also two diff families (`--diff-added-bg` and `--diff-add-line-bg`).
- **`accent` collision.** Tailwind `bg-accent` resolves to the brand colour, but shadcn's `--accent` is a hover surface. Any stock shadcn component renders wrong.
- **Radius mismatch.** `--radius-sm` is 3px in `tokens.css` but 2px in `@theme`.
- **Type-scale clash.** The `--text-xs…xl` vars collide with Tailwind's font-size namespace.
- **Undefined vars in use.** `--danger`, `--warning`, `--status-success-bg`, `--font-size-sm` and `--atlas-ants-color` are referenced but never defined.
- **Two ways of using a token.** 1,976 semantic utilities versus 2,581 `[var(--x)]` arbitrary classes.

### Coverage gaps
- **What themes never set.** Status colours (and `--status-success` is grey), agent chips, the tokens.css diff vars, comms surfaces, selection, `--text-accent` (`#ffff00`) and shadows.
- **Colour literals.** 686 in 141 files, including `bg-white` ×107, `bg-black` ×51 and 112 arbitrary `-[#…]` classes.
  - Worst folders: comms 85, components 66, spaces 51, terminal 45, organisations 41, chat 38, capture 37.
  - Worst files: `capture-popover.tsx`, `terminal-session.ts`, `chart-theme.ts`, `line-emulator.ts`, `feedback-panel.tsx`, `browser-panel.tsx`, `titlebar.tsx`.
- **Subsystems that ignore the theme:**
  - xterm uses a fixed One Dark palette (`terminal-session.ts:103`).
  - Chat, markdown and README code uses `highlight.js/styles/github-dark.css`.
  - The pixi knowledge and memory graphs use hex constants.
  - Recharts uses `mission-control/lib/chart-theme.ts`.
  - The xyflow dot grid is a hardcoded colour.
  - The launch background is black in both `index.html` and `lib.rs:133`.
- **What already follows the theme:** CodeMirror (through the editor theme), mermaid (reads vars at render time), sonner toasts, and the PDF chrome.

### shadcn compatibility
- **Missing tokens.** About 20 shadcn tokens exist. Missing: `chart-1..5`, all 8 `sidebar-*`, `font-serif`, `tracking-normal`, `spacing`, and `shadow-2xs/xs/xl/2xl`.
- **No shadcn setup.** There is no `components.json`, and `src/ui` has only `context-menu.tsx` and `tooltip.tsx`.
- **Direct Radix imports.** 66 files import Radix directly: dialog ×26, popover ×25, dropdown-menu ×16, context-menu ×3, tooltip ×1.

### File icons
- **Lucide only.** Every file is rendered with the same generic `File` icon (`tree-row.tsx:202-216`).
- **No icon theme exists.**

### Non-colour tokens (second audit, same day)

Atlas is a dense, px-based UI. Its real scales live in arbitrary values, not tokens.

- **Collisions change rendering.** `tokens.css` `:root` beats Tailwind's theme variables, so the utilities render Atlas values:
  - `text-xs` = 11px, `text-sm` = 12px, `text-base` = 13px
  - `rounded-sm` = 2px, `rounded` = `rounded-md` = 4px, `rounded-lg` = 6px
  - `shadow-lg`/`shadow-xl` still render Tailwind's 10%-black shadows, which are invisible on black.
- **Type.**
  - 95% of 1,427 size utilities are arbitrary: `[11px]` 533, `[10px]` 318, `[12px]` 180, `[9px]` 112, and about 130 half-steps (9.5, 10.5, 11.5, 12.5).
  - Weights: 500 and 600 only.
  - Fonts: system stacks only; no web fonts are loaded.
  - The de facto eyebrow label is `.eyebrow` (10px, semibold, uppercase, `tracking-wider`).
- **Spacing.** Code follows Tailwind's 4px grid with half-steps; `--space-*` has 0 references.
  - Control heights: 20 / 22 / 24 / 26 / 28 / 30 / 32 / 36px. 294 of 930 `h-*` utilities are arbitrary, and many duplicate a scale step.
  - Titlebar 30px, tab strip 36px, compact control 26px.
- **Radius.** 2 / 3 / 4 / 5 / 6 / 8 / 10 / 12 / 16px and full are all in use.
- **Elevation.**
  - One real shadow: `shadow-[var(--shadow-overlay)]`, used 83 times.
  - About 12 literal shadows, plus 17 inline inset top highlights.
  - 81 backdrop-blur uses, mostly `backdrop-blur-2xl`.
- **Z-index.** The tiers are nominal only.
  - `--z-sticky`, `--z-toast` and `--z-tooltip` are never used.
  - Nearly every floating layer sits at 9999 to 100000, and tooltips share 9999 with menus.
  - 56 inline `zIndex` values.
- **Motion.** No motion library.
  - `@theme` defines 3 easings and 5 animations. `tooltip-timing.ts` is the one fully specified system (from motion pass `e0e9178e`), and reduced-motion handling exists.
  - Otherwise, 17 hardcoded curves and about 15 distinct durations (80–450ms).
- **Icons.** Lucide sizes are set with `size=`: 11 (289), 12 (223), 10 (106), 13 (94), 14 (44), and others. `strokeWidth` takes 10 distinct values.
- **States.**
  - Disabled opacity varies: 30 / 40 / 45 / 50 / 60.
  - **There is no consistent keyboard focus indicator.** Outlines are removed globally, and `--ring` equals `--border-strong`.
- **Layout.**
  - Panel sizes are in % (`app-layout.tsx:140-162`), and px constants are scattered (detail panel 320/900/460, `CHAT_WIDTH = 420`, `PICKER_WIDTH = 460`).
  - Scaling uses native webview zoom (`ui-scale.ts`).
- **No component gallery.** `src/ui` has no Button, Input or Dialog primitive.

### Mock backend coverage (audit, 2026-09-18)

- **80 of 384 invoked commands are faked (80% unmocked); 3 of 37 event channels are emitted.** The app declares **388** `#[tauri::command]` fns — `CLAUDE.md` ("365") and `tests/ipc-contract.test.ts` both carry stale counts and should be corrected.
- **Works today:** titlebar, chat (best covered), file tree, knowledge (under `?scenario=knowledge`).
- **Empty today:** terminal, editor (mounts with no document), diff, PDF, memory, canvas, spaces, comms, mission control, log, artifacts, git graph, skills, packs, marketplace.
- **Settings renders but every control is inert** (`update_atlas_settings` returns `null`) — and settings is where a theme is chosen.
- **Only the Browser tab is genuinely impossible** (native `WebviewWindow`). The terminal is fakeable with scripted output through the real event channel; the editor needs an in-memory file system behind 4 commands.
- **Effort:** ~80–90 fakes to bring every non-impossible surface to at least PARTIAL. The first ~25 — editor/media (4), settings writes and BYOK (~8), log and mission control (5), git depth (~10) — unblock every theme-sensitive surface.

## Decisions

These are the answers from the grilling session with the maintainer.

| # | Decision |
|---|---|
| 1 | Full community ecosystem. Themes are a public contract, versioned with `schema = 1`. |
| 2 | Three levels per variant: **base tokens** (shadcn names, required) → **palette** (optional) → **theme keys** (optional). |
| 3 | "Applied everywhere" means everything: CodeMirror, xterm, diffs, chat code, graphs, charts, canvas, mermaid, PDF chrome and launch background. Documented exceptions: PDF page content and the native Browser webview. |
| 4 | Icon themes are a separate track that uses VS Code's `iconThemes` format verbatim. |
| 5 | Public docs go in `content/docs/themes/`; this page stays in `content/private`. |
| 6 | One file holds dark and/or light variants. Light variants ship behind a flag until every feature has been checked in light mode. |
| 7 | **One theme, one picker.** The editor-theme picker is removed. Users tweak colours with `themeOverrides`. |
| 8 | The existing 16 themes merge into about 14 full themes. Rosé Pine gains Moon and Dawn. |
| 9 | Theme keys use Zed-style dotted role names. Base tokens keep shadcn names verbatim. |
| 10 | Theme files are **TOML** and come with a published JSON Schema (`#:schema`). No key may be both a leaf and a prefix of another key. |
| 11 | Sources: built-in themes, `~/.config/atlas/themes/` (hot reload), and Open VSX for VS Code icon themes. A community index from an `atlas-themes` GitHub repo is **out of scope** — the repo is not being created, so nothing depends on it. |
| 12 | Material Icon Theme (MIT) is bundled as the default icon theme, loaded lazily. "Minimal" (lucide) remains an option. vscode-icons is **not** bundled, because its icons are CC BY-SA. |
| 13 | Chat, markdown and diff code use the theme's `syntax.*` keys. The highlighting engines stay as they are (no Shiki). |
| 14 | Resolution happens in TypeScript and produces a fully resolved variable map. No `color-mix()` or relative colour syntax: the minimum is macOS 11 / WKWebView. |
| 15 | Imports (shadcn/tweakcn, Zed, VS Code colour themes) are one-time conversions to TOML. |
| 16 | Radix → Base UI migration is in scope. It gets its own PR, after the token core and before the colour sweep. |
| 17 | The work lays the **design-system foundation**, not just theming: colour, typography, spacing, radius, elevation (shadows and z-index), motion, icon sizes, focus and disabled states, and density. A **Foundations** PR after PR 1 (it may run alongside PR 2) sets the scales and their lint guards; the colour sweep then moves code onto the final names in a single pass. |
| 18 | Colour has **role tokens only**: no raw 12-step ramps and no component-token tier. A theme key exists only when a theme author needs that component to differ from the base tokens. |
| 19 | Non-colour scales use **Tailwind v4's own namespaces** (`--text-*`, `--radius-*`, `--shadow-*`, `--ease-*`, `--spacing`), plus a custom `--z-*`. `--space-*` is deleted. |
| 20 | A theme may set radius, fonts, shadows and tracking. Spacing and the type scale are app-owned: imports keep tweakcn's `spacing` value but ignore it and show a warning. If density exists, it is a user setting. |
| 21 | A dev-only design-system scenario in the browser mock renders every token and `src/ui` primitive in the active theme. It is built in the Foundations PR and used by every visual check. |
| 22 | Theme-author docs go in the public `content/docs/themes/`. The design-system reference lives in the atlas repo at `docs/reference/design-system.md`, next to the code. |
| 23 | Snapping existing values to the scale **is allowed** in Foundations and the colour sweep. Every shift is checked with before/after screenshots on the design-system scenario. |
| 24 | **Type scale.** `3xs` 9, `2xs` 10, `xs` 11, `sm` 12, `base` 13, `md` 14, `lg` 16, `xl` 20, `2xl` 24 (px). Half-pixel sizes round up. Named text styles as `@utility`: `eyebrow`, `label`, `body`, `caption`, `code`, `heading`. Weights 500 and 600 only. |
| 25 | **Control heights.** `--control-xs` 20, `sm` 24, `md` 26, `lg` 32. 22, 28 and 30 snap to the nearest step. Titlebar (30) and tab strip (36) are named layout constants. |
| 26 | **Radius** derives from the theme's `--radius` (default 8px): `sm` = r−4, `md` = r−2, `lg` = r, `xl` = r+4, plus `full`. Bare `rounded` = `sm`. Use `sm` for controls, `md` for cards, `lg` for popovers, `xl` for dialogs. |
| 27 | **Elevation.** `shadow-sm` (raised), `shadow-md` (menus and popovers), `shadow-lg` (dialogs), an `inset-highlight` utility, and one `--blur-glass`. Shadow colour comes from the theme. The one-off shadows are deleted. |
| 28 | **Z-index layers.** `panel` 10, `titlebar` 40, `overlay` 100, `modal` 110, `popover` 200 (above modals), `toast` 300, `tooltip` 400, `drag` 500. Arbitrary z-index ≥ 60 and inline numeric `zIndex` are banned. |
| 29 | **Motion.** `--duration-instant` 80, `fast` 120, `base` 180, `slow` 260. Only the three existing easing curves are allowed. `tooltip-timing.ts` is the model for how a component specifies its motion. |
| 30 | **Icons** go through a `src/ui/icon.tsx` wrapper. Sizes 10 / 12 / 14 / 16 / 20 (11→12, 13→14, 9→10), default stroke width 1.75. |
| 31 | **States.** A global `:focus-visible` ring (2px, `var(--ring)`) replaces `outline: none`, and `--ring` is a real accent. Disabled is `opacity-50` plus `cursor-not-allowed`. |
| 32 | **Primitives.** The Base UI PR builds Dialog, Popover, Menu, ContextMenu and Tooltip. Foundations adds Button, IconButton, Input, Badge and Kbd, with variants from `class-variance-authority` (the one approved new dependency) sized on the control heights. |
| 33 | **Enforcement.** An 11th contract test bans arbitrary text-size, z-index, shadow and radius values, colour literals, `bg-white`/`bg-black`, and inline numeric `zIndex`, `fontSize` and `boxShadow`. It works as a ratchet: during the sweep the count only goes down, and it must be zero (apart from an allowlist) before the sweep merges. |
| 34 | The browser mock backend is extended until **every surface renders something plausible**, so a theme change can be judged everywhere. Faking all 365 commands is not the goal; the unmocked badge reaching zero is a side effect. |
| 35 | It is its own PR, queued straight after PR 1 and before Foundations and PR 2, because both are checked through it. |
| 36 | Fixtures cover **states, not just happy paths**: long names, errors, loading, empty, selected, disabled, unread, conflicted, running, cancelled. Colour lives in states. |
| 37 | The terminal and editor are faked too — scripted PTY output through the real event channel, and an in-memory file tree — so xterm and CodeMirror render real content with real theming. |
| 38 | One rich `default` scenario covers every surface in a single session; focused scenarios (`git-conflict`, `chat-tools`, knowledge) stay for specific states. |
| 39 | Surfaces that cannot be faked (native Browser webview, Finder drag-and-drop, native window chrome) render a labelled placeholder naming them as native-only, and are listed in the docs as the known exceptions of decision 3. |
| 40 | **The review loop.** The orchestrator never checks visuals itself: an implementer agent writes the code, a review agent opens it in Chrome. When a surface fails because a command it needs is unmocked, that is a mock gap, not a defect in the work under review — it is fixed by extending the mock backend (a follow-up implementer agent), then re-reviewed. Over the sequence this grows mock coverage until the whole app is inspectable. |
| 41 | **Keep the mock Storybook-ready** (do this in the next task that touches the mock backend). Two cheap affordances, both far easier now than retrofitted: (a) the installer takes an explicit scenario argument instead of only reading `?scenario=` from the URL, so a future Storybook decorator can pass one; (b) a store-reset helper lands alongside the fixtures, so per-story isolation is possible without bleeding Zustand singleton state. Storybook itself is NOT in scope — this only avoids painting it into a corner. |
| 42 | **The key registry is generated from one source of truth.** A hand-edited TOML file describes every theme key — its description, what it derives from, and the operation (`alpha`, `mix`, `lighten`, `towardBackground`…) — and everything else is generated from it: the TS registry, the Rust key list, the key enum inside `theme-v1.json` (so `#:schema` catches an author's typo), `docs/reference/theme-keys.md`, and the public token table. Today the same facts live in five places, which is how a 134-vs-135 drift and a mis-documented scrollbar rule both survived review. Derivation rules are a small closed vocabulary, so they are data, not code. Format split: **TOML** for anything a human authors (themes, this source file), **JSON** for anything a machine consumes (the schema — JSON Schema has no TOML form and the TOML editor tooling fetches JSON — plus generated snapshots and IPC payloads). |

## Theme file shape (schema 1)

```toml
#:schema https://docs.tryatlas.cc/schema/theme-v1.json
schema = 1
id = "rose-pine"
name = "Rosé Pine"
author = "Rosé Pine"
license = "MIT"

[dark.base]            # shadcn names, verbatim
background = "#191724"
foreground = "#e0def4"
primary = "#c4a7e7"
primary-foreground = "#191724"
# … card, popover, secondary, muted, accent, destructive, border, input, ring,
#   chart-1..5, sidebar-*, radius, font-sans/serif/mono, shadow-*, tracking-normal

[dark.palette]         # optional
red = "#eb6f92"
yellow = "#f6c177"
# … orange, green, cyan, blue, purple, pink

[dark.keys]            # optional; nested tables and quoted dotted keys are equivalent
"element.hover" = "#26233a"
terminal.ansi.red = "#eb6f92"
syntax.keyword = { color = "#31748f", font_style = "italic" }

[light.base]           # optional second variant
background = "#faf4ed"
```

**Loader.** Rust flattens nested tables into dotted keys. It rejects unknown base tokens, unknown top-level fields, and any key that is both a leaf and a prefix. Unknown theme keys produce a warning, not an error, so that newer themes still load on older Atlas builds.

**User config (`config.toml`):**
```toml
theme = "rose-pine"
themeMode = "system"   # system | dark | light
[themeOverrides.keys]  # same shape as a variant, applied to the active variant
"syntax.comment" = "#6e6a86"
```

If the variant the mode asks for is missing, Atlas uses the theme's other variant.

## Resolution

For each theme key: explicit → palette rule → base rule → Atlas default for the appearance. The rules live in one TS table next to the key list, so each key has exactly one rule.

**Resolver output.** A flat `Record<cssVarName, string>` and a typed object for JS consumers (xterm, pixi, recharts).

**Required tests:**
- Every built-in theme resolves every key.
- Every CSS var the app references is either produced by the resolver or defined in `tokens.css`.
- No resolved value is empty.

### Working rules for this run

- **One agent per worktree at a time.** Two agents in a shared tree cannot distinguish each other's half-finished work from breakage, and they share a git index (observed: a mock agent nearly committed the rename agent's staged files). Parallelism only across separate worktrees — which the sweep will use.
- **The orchestrator reviews nothing itself.** Every PR is checked by a review agent that runs the gates, reads the diff against the spec, and opens the app in Chrome, then reports a verdict with specifics (decision 40). The orchestrator only dispatches, arbitrates (e.g. "this failure is a mock gap, not a defect in this PR") and keeps the queue moving. Reviews are read-only: a review agent never fixes what it finds — a follow-up implementer does.
- **Model choice is justified per launch.** Opus where judgement or cross-type correctness is needed (fixtures typed against unfamiliar APIs, the rename's collisions, Foundations, Base UI, importers); Sonnet where the compiler or a test is the oracle (the sweep, mechanical moves, read-only review).
- **Never run `cargo test -p atlas-theme -p atlas-icon-theme -p atlas` in one invocation.** Combining them makes cargo's feature unification pull `serde_json/preserve_order` in through the codex dependency graph reachable via `-p atlas`, which changes JSON key ordering and spuriously fails `atlas_theme::tests::generated_schema_is_current` (it compares the schema byte for byte). Run each crate in its own invocation, which is what CI's per-crate matrix does anyway. It is not a regression.
- **Shared `/target` across worktrees serves stale artifacts.** Agents share `CARGO_TARGET_DIR` (recompiling the 1,161-crate graph per worktree is not affordable), and cargo keys a crate's artifacts by one metadata hash regardless of which worktree built it — so a sibling's build can make `cargo` here see a "fresh" rmeta missing your modules. Symptom: `cannot find … in atlas_theme` against source that plainly has it. Fix: `touch` the crate's sources and re-run. Two agents hit this.
- **Codex is not used** — the user's Codex quota is spent; Claude subagents only.
- Commits are local, conventional, and never carry a Co-Authored-By or attribution footer.

## PR framing (maintainer's words, for the description)

The diff is large, and a lot of it is the mock IPC backend rather than the theme work. That is deliberate and worth saying plainly in the PR:

- **It lays the foundation for a Storybook design system later.** The expensive half of Storybook for this codebase is a swappable IPC layer with typed fakes and fixtures that cover real states; that now exists, along with an installer that takes an explicit scenario and a store-reset helper (decision 41).
- **It cuts developer machine load.** Frontend work no longer needs a Rust build: `bun run dev` boots in ~140 ms against the fakes, where `dev:app` costs minutes. Reviewing a UI change no longer means compiling 1,161 crates.
- **It restores something that used to be true.** In Atlas's early days the README said you could run `bun run dev` for frontend work. That stopped being true as the app grew and commands multiplied; this brings it back.

## Key-set audit (2026-09-18) — cut 135 keys to ~72

A read-only audit reimplemented the resolver and ran it against all 16 shipped variants. Queued as its own stage, to land **after** Base UI and the palette fixes merge and **before** the sweep, so the sweep rewrites call sites to final names once.

**Evidence:** 81 of 135 keys are set by no shipped theme; 12 are set by every theme to exactly their derived value; every theme file is structurally identical (a mechanical conversion, not 15 authorial judgements — so "all themes agree" is weaker evidence than it looks, and is trusted here only for exact synonyms of a base token and for zero-consumer keys).

**Two structural facts:** removing a key is a *soft* break (unknown keys load with a warning — `lib.rs:517-528`), unlike unknown base tokens or palette colours, which are hard errors. And `theme-v1.json` types `keys` as an open map, so `#:schema` validates nothing at level 3.

**Top changes, in value order**
1. Fix the built-in palettes first — every "this derives fine" argument depends on it (already in flight on `uzayer/palette-fixes`).
2. **Agent chips 18 → 2** (`agent.chip.foreground`/`.background`). Only 6 agent identities exist, so 8 keys colour nothing; 3 more are overridden by hardcoded CSS. ADR-0002 forbids privileging agents, and the set is discovered at runtime so an author cannot enumerate it. The 2 survivors let a monochrome theme (`atlas-mono`, `vesper`) flatten the brand colours.
3. **Delete all 8 `comms.*`** — three have zero consumers; the rest are `sidebar`, `background`, `status.success`, `status.info` under local names.
4. **Delete the 12 exact restatements**: `border.default`, `border.variant`, `text.muted`, `text.accent`, `text.placeholder` (nothing reads it, and its rule is backwards), the three `tab.*`, `panel.elevated.background`, `panel.overlay.background`, and merge `panel.rail.background` into `panel.background`.
5. **Merge `border.focus` into `border.strong`, re-sourced from `border` not `ring`.** Live bug: since decision 31 made `ring` a real accent, an unset theme gets a brand-coloured border. Wrong in 15 of 16 variants.
6. **Diff family 14 → 7**, renamed to `diff.<state>.<role>` (`diff.added.background`/`.emphasis`/`.text`, same for removed), absorbing `stat.*` and `capture.live`.
7. **Add `search.match.background` / `search.match.active_background`** and delete the `rgba(249,115,22,…) !important` in `globals.css:1630-1638` — a hardcoded orange that clashes in every theme and is unreadable in light.
8. **Generate the key names into `theme-v1.json`** so `#:schema` catches typos.
9. **Decide `font_style`**: wire it through the resolver or drop it from the schema — it is in the Rust type, the TS type, the JSON Schema and the spec's example, and `resolve-theme.ts:25-27` discards it.
10. Also delete: `ghost_element.*` (zero consumers anywhere), `status.purple`/`status.orange` (palette slots wearing a status name), `atlas.ants` (always overwritten inline), `syntax.punctuation`/`syntax.builtin` (the app already routes them elsewhere), `scrollbar.track.background` (the track is painted transparent), `editor.fold.*` (derive), the four status backgrounds (derive at alpha 0.12), `terminal.selection` (derive).

## PR sequence

**One branch, one PR.** Every stage below lands as commits on the single branch `worktree-agent-afbf978575d0248fb`, which opens as **one PR into `0.3.3` at the very end**. The "PR" numbering is a sequencing device, not separate pull requests: nothing is opened or pushed until the whole scope is finished. Commits stay logical and per-stage so the one PR is readable.

**Division of labour.** A Codex agent implements each PR in its own worktree; a Claude agent reviews the diff and checks the result visually. Codex never builds or runs the Tauri app: its Rust obligation is `cargo check --workspace` plus the crate's tests. Visual checking runs on `bun run dev` (the browser mock backend) in Chrome, which needs no Rust build — so every PR must keep the mock fakes complete and correctly typed.

Every PR branches from the current version branch (`0.3.3`), keeps all gates green (`bun run lint`, `format:check`, `typecheck`, `test`; `cargo check --workspace` and the relevant `cargo test -p` when Rust changes), and ends with a visual check in the browser mock (`bun run dev`).
