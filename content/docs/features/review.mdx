title: Review
description: A second opinion on a change, before it goes anywhere.
---

Review runs a model over a set of changes and reports back per file. It's a tab in the right panel, next to [Source Control](/docs/features/git).

The point is that the model reviewing isn't the model that wrote the code. You pick the provider and model yourself, from the keys in [Settings → API Keys](/docs/features/settings), so you can have one vendor's model read another's output.

![The Review panel showing per-file verdicts for a set of changes](/screenshots/placeholder.svg)

## What to review

Four sources, chosen before you run it:

- **Working**: everything uncommitted.
- **Staged**: only what you've staged.
- **Commit**: a specific commit, picked from the log.
- **Branch**: a whole branch's changes.

You can also start a review from a commit in [Source Control](/docs/features/git)'s History view.

## The report

The report opens with an overall summary, a risk score, an estimate of how much effort the change takes to review, notes on security concerns and test coverage, and (when the change is structural enough to warrant one) a generated architecture diagram.

Below that is a card per file: a summary, a risk level of low, medium, or high, and the specific issues found, each anchored to the lines it's about so you can jump straight there.

Files the review didn't cover are listed explicitly rather than omitted, so a short report doesn't read as a clean bill of health.

Each run records the tokens it used and what it cost.

## Acting on it

A finding is a starting point, not a verdict. You can send the report (or a single file's findings) straight into a [chat](/docs/features/chat) as a prompt, which turns a review comment into work an agent picks up with the full context already attached.

Reports can also be copied out as markdown.

Reviews are saved, so you can reopen an earlier one rather than paying to run it again.
