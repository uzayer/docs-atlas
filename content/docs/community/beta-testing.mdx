## What to test

Each release has focus areas: the parts that changed most, or that we know least about. We post them in the Atlas Contributors announcements channel when a build is ready. {/* TODO(founders): confirm the channel name (proposed: #announcements) and who posts the focus areas for each release. */}

Between releases, these are always worth your time, because they are where a team works together:

- **[Timeline](/docs/team/timeline).** Do your sessions and your teammates' show up, live, with the right checkpoints? Do comments land where you put them?
- **[Team chat](/docs/team/chat).** Channels, direct messages, mentions, attachments and session references.
- **[Calls](/docs/team/calls).** Starting a call from a conversation, joining it in the browser, and finding the recording afterwards.
- **[Prompt drafts](/docs/team/prompt-drafts).** Two or more people editing the same draft at once, then one of you sending it.
- **[Shared threads](/docs/team/shared-threads).** Several people and agents on the same changes. Parts of it are still arriving in the desktop app; that page says which.
- **[Atlas Agent](/docs/agents/atlas-agent).** Coding with it, asking it what a teammate is working on, and having it reply to comments or post a session report.

For what changed in the release you're on, read its section of the [changelog](/docs/community/changelog).

## Report a bug

A short report is fine. A report we can reproduce is better. The difference is usually the session.

### Attach the session

When an agent was involved, the recorded session is the most useful thing you can send. It holds the prompts, the tool calls and their results, and the edits, in order, so we can see what led up to the problem instead of guessing.

Find the session on the [timeline](/docs/team/timeline), then either:

- **Export it.** Open the session and select **Export session** to save it as Markdown or JSON, then attach the file to your report.
- **Share a link.** For a session in a cloud project, select **Share session** in the [web app](/docs/team/web-app#share-a-session-publicly) and choose **Anyone** to create a read-only public link. You can add a password, and stop sharing once we're done.

A session can contain file contents and command output from your project. Atlas redacts secrets such as API keys and tokens before it stores a session, but read it before you send it, and don't share a session from code you can't show us.

If Atlas Agent misbehaved, an organisation admin can also open a short **prompt capture** window so we can see the exact requests. See [AI access](/docs/team/ai-access#your-prompts).

### Include your version and platform

- **Atlas version:** **Settings → About**, or at the bottom right of the rail.
- **Operating system and version**, and for Linux, which package you installed (deb, rpm, AUR, AppImage or tarball).
- **Which agent** was active, and its model.

### Include the logs, if something failed silently

Atlas writes its own log to a file, kept for the last seven days:

| Platform | Location |
| --- | --- |
| macOS | `~/Library/Logs/dev.atlas.ide/` |
| Windows | `%LOCALAPPDATA%\dev.atlas.ide\logs\` |
| Linux | `~/.local/share/dev.atlas.ide/logs/` |

Attach the newest `atlas.*.log`, or the lines around the time it happened. These logs are Atlas's own messages, not your prompts or code.

When an external agent never finishes starting, the chat shows a notice with **Copy diagnostics**. It copies the agent's install state and the recent log in one block; paste it into your report.

The **Log** tab (open it from **More** in the rail) is something else: a per-project activity log of what Atlas did, which you can pin entries in. A screenshot of it can help too.

### A template

Copy this, fill in what you have, and delete the rest.

```md
**What happened:**
**What I expected:**
**How to see it:** (steps, or "happened once")
**Session:** (exported file or share link)
**Atlas version / OS:**
**Agent and model:**
**Logs or diagnostics:** (attached, or the relevant lines)
```

### Where to send it

Post it in the Atlas Contributors bugs channel, or open a [Bug Report on GitHub](https://github.com/pacifio/atlas/issues/new?template=bug_report.yml). The GitHub form needs only a description; everything else is optional. Check the [open issues](https://github.com/pacifio/atlas/issues) first, and add a reaction to an existing one rather than filing a duplicate.

## Give feedback

Feedback that isn't a bug is just as useful: something slow, clumsy or confusing, or something you expected Atlas to do.

- **From the app.** Select the **?** at the bottom of the rail, then **Send feedback**, or use **Send feedback** in **Settings → General**. Pick **Issue**, **Feature request**, **Improve** or **Other**, and on macOS attach a screenshot if it helps. See [Feedback](/docs/community/feedback#from-the-app).
- **In Atlas Contributors chat.** Use the feedback channel for anything you'd rather talk through. {/* TODO(founders): confirm the channel name (proposed: #feedback). */}
- **On GitHub.** The [Feature Request / Feedback](https://github.com/pacifio/atlas/issues/new?template=feedback.yml) form.
